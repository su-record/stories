# vica 개발일지: GitHub 이슈를 제보로 가져오고 응답 대기까지 연결하기

2026년 11월 5일의 vica 작업은 GitHub 이슈를 컴패니언의 제보 처리 흐름에 연결하는 데 초점을 맞췄습니다. 이슈를 가져와 제보로 저장하는 명령을 추가하고, 컴패니언이 GitHub 제보를 분류·검증해 응답 대기에 알리는 화면과 흐름을 다뤘습니다. Rust 코드에는 rustfmt를 적용해 서식을 맞췄습니다.

이번 기록은 최근 커밋 세 개의 메시지를 바탕으로 정리했습니다. 코드와 실행 결과까지 확인한 내용은 아니므로, 구현 범위와 아직 설명할 수 없는 부분을 구분해 남깁니다.

## 컴패니언: GitHub 이슈를 제보로 저장하기

컴패니언 영역에는 GitHub 이슈를 가져와 제보로 저장하는 명령이 생겼습니다. 이번 변경에서 눈여겨볼 부분은 가져온 이슈의 저장 목적지가 ‘제보’라는 점입니다. GitHub에 작성된 이슈를 vica에서 제보로 다룰 수 있는 진입 경로를 추가한 셈입니다.

이 명령의 역할은 이슈를 가져오는 단계부터 제보로 남기는 단계까지입니다. 뒤에서 다룰 분류·검증 흐름과 함께 보면, 외부 이슈가 들어오는 입구와 들어온 제보를 처리하는 과정이 각각 마련됐다고 정리할 수 있습니다.

다만 명령의 이름과 인자, 가져올 이슈의 범위는 커밋 메시지에 나오지 않습니다. 같은 이슈를 다시 가져왔을 때 어떻게 처리하는지도 알 수 없어, 이번 일지에는 구체적인 사용 예시나 중복 처리 방식을 싣지 않았습니다.

## 채팅 화면과 흐름: 분류·검증 결과를 응답 대기에 알리기

채팅 영역에서는 컴패니언이 GitHub 제보를 분류·검증하고, 이를 응답 대기에 알리는 화면과 흐름을 추가했습니다. 제보를 저장하는 기능에서 한 단계 더 나아가, 들어온 제보를 살펴본 뒤 응답 대기 쪽으로 연결하는 부분을 다룬 작업입니다.

여기서는 ‘응답 대기에 알린다’는 범위를 분명히 해두려 합니다. 커밋 메시지로 확인할 수 있는 것은 분류·검증과 응답 대기 알림까지입니다. 실제 답변을 작성하거나 GitHub 이슈에 답변을 게시하는 기능까지 추가됐다고 볼 근거는 없습니다.

분류 기준이나 검증 항목도 아직 이 기록만으로는 설명하기 어렵습니다. 검증을 통과하지 못한 제보가 어디로 가는지, 응답 대기 화면에 어떤 정보가 표시되는지는 구현을 살펴봐야 합니다. 따라서 이번 변화는 **GitHub 제보를 처리해 응답 대기에 알리는 화면·흐름의 추가**로 정리하는 것이 정확하겠습니다.

## Rust 코드: rustfmt로 서식 맞추기

기능 작업과 별도로 Rust 코드의 서식을 rustfmt로 맞췄습니다. 이 변경은 제보 처리 기능과 구분해서 기록합니다. 커밋 메시지에 드러난 목적은 코드 서식 정리이며, 동작 변경이나 성능 개선을 포함했다고 설명할 근거는 없습니다.

서식 변경과 기능 변경은 코드를 검토할 때도 확인할 지점이 다릅니다. 전자는 표현 형식을, 후자는 제보가 들어오고 처리되는 동작을 중심으로 봐야 합니다. 이번 일지에서도 두 영역을 나눠 변경의 성격이 섞이지 않도록 했습니다.

## 이번 작업의 연결점과 확인할 부분

세 커밋을 기능별로 묶으면, GitHub 이슈를 제보로 저장하는 입구와 그 제보를 분류·검증해 응답 대기에 알리는 흐름이 핵심입니다. Rust 서식 정리는 이와 별개의 코드 정돈 작업입니다.

실제 사용 흐름을 확인할 때는 가져온 제보가 분류·검증을 거쳐 응답 대기에 어떻게 나타나는지 살펴볼 필요가 있습니다. 재가져오기와 검증 실패 상황도 확인 대상입니다. 현재 자료만으로 이 동작들이 검증됐다고 말할 수는 없지만, 이번에 추가한 기능의 범위와 다음에 확인해야 할 경계는 구분해둘 수 있었습니다.
