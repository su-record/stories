## 프롬프트 한 장은 직원이 아니다

![프로필·스킬·메모리의 역할 분리](/images/assemble-ai-employee-operations/01.png)
*섞지 말고 조립*


“회의를 요약하고 후속 업무를 정리해 줘.” 처음에는 이 정도 지시로 충분해 보입니다.

문제는 그다음입니다. 지난주 결정과 이번 주 발언이 충돌합니다. 담당자 이름을 잘못 연결합니다. 외부로 보내면 안 되는 초안까지 공유합니다.

긴 시스템 프롬프트로 해결하려는 접근은 틀렸습니다. 역할과 절차, 기억, 권한이 한 문서에 뒤섞이기 때문입니다. 한 부분을 고치면 다른 행동까지 달라집니다.

2026년 7월 25일 기준, Genspark Claw는 30개 이상 스킬과 메모리 시스템, 워크플로우, 팀 커뮤니케이션, 회의 봇을 묶어 ‘나만의 AI 직원’으로 소개합니다. 중요한 숫자는 30이 아닙니다. 각 기능이 분리된 구성요소라는 점입니다.

AI 직원은 하나의 모델이 아닙니다. 프로필과 스킬, 메모리를 워크플로우로 연결한 운영 시스템입니다.

---

## 프로필·스킬·메모리는 서로 다른 문제를 푼다

![메모리는 후보·승인·장기 저장의 흐름으로 관리한다](/images/assemble-ai-employee-operations/02.png)
*승인된 기억만 저장*


세 요소를 섞으면 수정 범위가 커집니다. 프로필은 판단 기준을 고정하고, 스킬은 작업 절차를 정의합니다. 메모리는 다음 실행에 필요한 맥락만 보존합니다.

| 구성요소 | 답해야 하는 질문 | 포함할 내용 | 넣지 말아야 할 내용 |
|---|---|---|---|
| 프로필 | 어떤 기준으로 판단하는가 | 역할, 목표, 금지사항, 보고 대상 | 매번 달라지는 작업 순서 |
| 스킬 | 일을 어떻게 수행하는가 | 입력, 도구, 단계, 출력 형식, 실패 처리 | 장기 사용자 취향 |
| 메모리 | 다음에도 무엇을 기억하는가 | 결정, 선호, 관계, 근거, 만료일 | 회의 전문 전체 |
| 워크플로우 | 언제 무엇을 연결하는가 | 트리거, 실행 순서, 승인 지점 | 암묵적인 예외 처리 |
| 권한 | 어디까지 실행할 수 있는가 | 읽기·쓰기·전송 범위 | 포괄적인 관리자 권한 |

예를 들어 프로필에 “마케팅을 돕는다”라고 쓰면 판단 기준이 없습니다. “고객 인터뷰 근거로 주간 제품 인사이트를 작성하며, 근거 없는 추정은 별도 표시한다”까지 내려가야 합니다.

스킬은 재사용 가능한 작업 계약입니다. 회의 요약 스킬이라면 입력 형식, 필수 출력, 사용할 문서, 정보가 부족할 때의 중단 조건이 필요합니다.

메모리는 대화 기록 보관함이 아닙니다. “가격 인상 반대”만 저장하면 누가, 언제, 어떤 조건에서 반대했는지 사라집니다. 출처와 유효기간이 빠진 기억은 곧 잘못된 지시가 됩니다.

## 한 가지 업무부터 조립한다

![문서 읽기 권한과 외부 전송 권한의 분리](/images/assemble-ai-employee-operations/03.png)
*읽기와 전송 분리*


처음부터 범용 비서를 만들 필요는 없습니다. 테스트하기 좋은 업무는 매주 12개의 고객 인터뷰 기록을 읽고, 금요일 오후 4시에 한 장짜리 보고서를 만드는 일입니다.

출력 조건은 네 가지로 제한합니다.

- 핵심 문제를 최대 5개까지 정리합니다.
- 각 주장에 회의 링크와 발언 시각을 붙입니다.
- 지난주 결정과 충돌하면 별도 표시합니다.
- 초안은 제품 책임자 승인 전까지 외부로 전송하지 않습니다.

이 조건을 설정 파일로 옮기면 책임 범위가 선명해집니다.

```yaml
employee:
  id: customer-insight-01
  profile:
    role: 고객 인터뷰 분석 담당
    goal: 반복되는 고객 문제와 근거를 주간 단위로 정리
    reports_to: product-owner
    rules:
      - 근거 없는 추정은 hypothesis로 표시
      - 개인정보는 출력에서 제거
      - 외부 전송은 승인 이후에만 허용

  skills:
    - transcript-cleaner
    - evidence-extractor
    - weekly-brief-writer
    - decision-conflict-checker

  memory:
    read:
      - product-decisions
      - customer-segments
      - writing-preferences
    write:
      - confirmed-decisions
      - approved-preferences

  workflow:
    trigger: '0 16 * * 5'
    approval_required: true
    destination: notion-draft
```

각 스킬도 이름만 등록하면 부족합니다. `evidence-extractor`의 입력은 회의 전문과 참석자 목록입니다. 출력은 주장, 인용문, 시각, 출처 링크, 신뢰도입니다.

전문이 없거나 시각 정보가 깨졌다면 요약을 강행하지 않습니다. `insufficient_source` 상태로 멈추고 담당자에게 원문을 요청합니다. 실패를 숨기지 않는 것도 스킬 계약입니다.

Schift가 다루는 문서·권한 기반 인프라는 이 지점과 연결됩니다. 문서를 읽을 수 있다는 사실과 외부로 전송할 수 있다는 권한은 분리해야 합니다. Hermes Agent가 다루는 AI 네이티브 업무 시스템도 개별 답변보다 학습과 업무 흐름의 연결에 초점을 둡니다.

## 메모리는 저장량보다 쓰기 규칙이 중요하다

메모리를 많이 쌓으면 개인화될 것이라는 기대가 있습니다. 실제로는 오래된 결정과 일시적인 의견이 함께 검색되면서 충돌이 늘어납니다.

저장 단위에는 최소 여섯 항목이 필요합니다.

```yaml
memory:
  type: decision
  content: 무료 체험 기간을 14일로 유지
  source_id: meeting-2026-07-18-03
  owner: product-owner
  confidence: confirmed
  expires_at: 2026-10-31
  visibility: product-team
```

`content`만 저장하면 안 됩니다. `source_id`는 검증 경로를 남깁니다. `owner`는 수정 권한을 정합니다. `expires_at`은 오래된 결정을 자동으로 재검토하게 만듭니다.

메모리 쓰기는 세 단계로 제한할 수 있습니다.

1. AI가 저장 후보를 제안합니다.
2. 담당자가 승인·수정·거절합니다.
3. 승인된 항목만 장기 메모리로 이동합니다.

loopy-me-farm 개발 기록은 개인 사용 패턴과 루틴을 학습하는 어시스턴트, Skill Optimizer Agent를 프로필·스킬·메모리·피드백 루프로 다룹니다. 여기서 가져올 핵심은 자동 학습 자체가 아닙니다. 사용자의 수정이 다음 실행 규칙으로 변환되는 구조입니다.

예를 들어 사용자가 보고서 제목을 6주 연속 고쳤다고 가정합니다. 수정 이력 20건을 모은 뒤 제목 스킬의 변경안을 제안할 수 있습니다. 자동 반영은 막고, 담당자가 차이를 확인한 뒤 새 버전을 승인합니다.

## 평가는 말투가 아니라 재작업으로 한다

“답변이 자연스럽다”는 운영 지표가 아닙니다. 결과를 얼마나 다시 고쳤는지, 근거가 빠졌는지, 승인 경계를 넘었는지를 기록해야 합니다.

| 지표 | 운영 기준 예시 | 측정 방법 |
|---|---:|---|
| 근거 첨부율 | 100% | 주장별 출처 링크 검사 |
| 무단 외부 전송 | 0건 | 전송 로그와 승인 로그 대조 |
| 누락된 필수 항목 | 실행당 0개 | 출력 스키마 검증 |
| 사람의 수정량 | 첫 4주 기준선 측정 | 수정 전후 문장 차이 비교 |
| 잘못 검색된 메모리 | 주간 표본 10건 중 0건 | 담당자 수동 검토 |
| 중단 조건 준수율 | 100% | 실패 상태와 후속 행동 확인 |

첫 4주는 성능을 자랑하는 기간이 아닙니다. 기준선을 만드는 기간입니다. 수정 이유를 `사실 오류`, `근거 부족`, `형식`, `권한`, `취향`으로 나누면 어디를 고칠지 보입니다.

사실 오류는 모델이나 검색 단계를 점검합니다. 형식 문제는 스킬을 수정합니다. 반복되는 취향은 승인 후 메모리에 넣습니다. 권한 문제는 프롬프트가 아니라 실행 인프라에서 차단합니다.

조립 순서도 단순합니다. 한 업무를 고르고, 프로필을 고정하고, 스킬 계약을 작성합니다. 승인된 정보만 메모리에 남긴 뒤 실행 로그와 수정 이력을 연결합니다.

모델을 교체하기 전에 네 기록부터 확인해야 합니다. 어떤 판단 기준을 사용했고, 어떤 스킬 버전을 실행했으며, 어떤 메모리를 읽었고, 누가 결과를 승인했는지 남아 있어야 합니다. 기록이 없으면 다음 실행도 같은 프롬프트를 다시 돌리는 일에 그칩니다.
