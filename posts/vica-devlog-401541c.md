# vica 개발일지: 기억하고, 먼저 움직이고, 제대로 보여주는 데몬

이번 작업에서는 `vica`의 데몬을 단순히 요청에 반응하는 실행기에서 한 단계 더 발전시키는 데 집중했습니다. 핵심은 세 가지였습니다. 실행 간 맥락을 기억하게 만들고, 데몬이 스스로 다음 행동을 시작할 수 있도록 하며, 사용자가 실제 세션에서 오간 내용을 정확히 확인할 수 있게 하는 것입니다. 여기에 새 기능을 안전하게 도입하기 위한 운영 설정과 검증 문서도 함께 정리했습니다.

## 실행은 기억하되, 평가는 독립적으로

먼저 컨텍스트 서브시스템을 추가해 여러 번의 실행이 이전 맥락을 이어받을 수 있도록 했습니다. 매번 완전히 처음부터 시작하는 방식은 구조가 단순하지만, 장기 작업에서는 이미 확인한 내용을 반복하거나 앞선 결정을 잃기 쉽습니다. 이제 실행 과정에서 필요한 기억을 남기고, 이후 실행이 이를 활용할 수 있습니다.

다만 기억이 모든 영역으로 무제한 전달되지는 않도록 경계를 뒀습니다. 특히 결과를 판단하는 평가 영역에는 누적 메모리가 직접 닿지 않게 했습니다. 과거의 해석이나 기대가 평가에 섞이면 결과가 편향될 수 있기 때문입니다. 편의성을 위해 기억을 도입하되, 판정의 독립성은 지키는 방향을 택했습니다. 이 분리는 조금 번거롭더라도 앞으로 신뢰도를 높이는 데 중요한 기반이 될 것 같습니다.

## 기다리기만 하던 데몬에 주도성 추가

배포되는 데몬에는 자체적인 initiative 인스턴스를 연결했습니다. 이제 데몬은 외부 요청이 들어올 때만 움직이는 구성에서 벗어나, 필요한 조건이 갖춰졌을 때 스스로 작업을 시작할 수 있는 기반을 갖췄습니다.

컨텍스트와 initiative는 모두 동작 범위가 큰 기능이라 한 번에 강제 활성화하지 않았습니다. 환경 설정을 통해 각각 명시적으로 켤 수 있도록 옵트인 방식을 적용했고, 현재 활성화 여부도 상태로 기록하게 했습니다. 운영 중 문제가 생겼을 때 “어떤 기능이 켜진 상태였는지”를 확인할 수 있어야 재현과 진단이 가능하기 때문입니다. 새 기능을 만드는 것만큼, 안전하게 끄고 상태를 추적할 수 있게 만드는 일도 중요하다는 점을 다시 확인했습니다.

## TUI가 실제 대화를 보여주도록

라이브 TUI에서는 표시되는 내용과 세션이 실제로 주고받은 내용 사이의 차이를 줄였습니다. 내부 처리용 데이터나 간접적으로 가공된 상태가 아니라, 세션에서 실제 발화된 내용을 기준으로 화면을 구성하도록 손봤습니다.

겉으로는 작은 표시 개선처럼 보이지만 디버깅 경험에는 차이가 큽니다. 사용자가 본 화면과 내부 기록이 다르면 문제를 설명하기도 어렵고, 로그를 다시 대조하는 비용도 커집니다. 이제 라이브 클라이언트만 봐도 세션의 흐름을 훨씬 솔직하게 파악할 수 있습니다.

## 현재 검증 상태 문서화

마지막으로 README의 검증 현황을 최신 측정 결과에 맞춰 갱신했습니다. 기능이 빠르게 늘어날수록 문서에 적힌 기대와 실제 상태가 어긋나기 쉬워서, 막연히 “동작한다”고 표현하기보다 확인된 범위를 기준으로 기록했습니다.

이번 변경으로 `vica`는 기억, 주도성, 관찰 가능성이라는 세 축을 갖추기 시작했습니다. 아직은 새 서브시스템을 기본 활성화하지 않고 조심스럽게 운영하는 단계입니다. 다음에는 실제 환경에서 축적되는 상태와 실패 사례를 살펴보며, 기본값을 바꿔도 될 만큼 안정적인지 검증해보겠습니다.
