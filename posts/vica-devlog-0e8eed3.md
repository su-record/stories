# 승인부터 비용, 실패 설명까지 다듬은 최근 작업

최근 `vica`에서는 새로운 기능을 크게 늘리기보다, 실행 과정에서 사용자가 답답하게 느낄 만한 지점을 정리했습니다. 이번 작업은 **스킬 권한 관리**, **대화형 요청의 prefill 처리**, **실행 결과 설명 개선**이라는 세 영역으로 나눌 수 있습니다. 서로 다른 부분처럼 보이지만, 결국 “시스템이 무엇을 했고 왜 그렇게 판단했는지 더 정확하게 보여주자”는 방향으로 이어집니다.

## 스킬 승인과 읽기 가능 여부 구분

먼저 authority 영역에서는 스킬을 승인할 수 있도록 흐름을 확장했습니다. 이제 스킬이 단순히 존재하는 것과 실제로 사용이 허용된 상태를 구분할 수 있습니다. 권한이 필요한 기능을 다룰 때는 이 차이가 꽤 중요합니다. 등록되었다는 이유만으로 바로 실행할 수 있게 두면 안전하지 않고, 반대로 승인 상태를 표현하지 못하면 운영 과정이 지나치게 수동적이기 때문입니다.

이 작업을 진행하면서 `vica`가 특정 스킬을 읽지 못하는 경우도 함께 드러났습니다. 처음에는 승인 문제처럼 보일 수 있지만, 실제로는 스킬 자체에 접근하거나 내용을 해석할 수 없는 상황이 별도로 존재했습니다. 승인되지 않은 것과 읽을 수 없는 것은 원인도 대응 방법도 다르기 때문에, 둘을 같은 실패로 뭉개지 않도록 구분하는 데 신경 썼습니다.

아직 모든 예외가 완벽하게 설명되는 것은 아니지만, 적어도 “권한이 없어서 못 쓰는지”, “애초에 읽을 수 없는지”를 나눠 볼 수 있는 기반은 마련했습니다.

## 매 턴 반복되던 prefill 비용 줄이기

provider 영역에서는 여러 턴으로 이어지는 요청의 비용 처리 방식을 손봤습니다. 이전에는 대화가 한 턴 진행될 때마다 prefill 부분까지 다시 비용을 지불하는 형태가 되어 있었습니다. 대화가 짧을 때는 크게 티가 나지 않지만, 턴이 쌓일수록 동일한 앞부분에 반복해서 비용이 붙는 문제가 있었습니다.

이번 변경에서는 prefill을 매 턴 새로 부담하지 않도록 처리 흐름을 조정했습니다. 핵심은 이미 제공된 문맥과 새로 추가되는 턴을 같은 비용으로 계속 계산하지 않는 것입니다. 덕분에 긴 대화나 반복 실행에서 불필요한 비용 증가를 줄일 수 있게 되었습니다.

비용 최적화는 눈에 보이는 기능은 아니지만 실제 사용성에는 직접적인 영향을 줍니다. 특히 provider별 과금 방식과 요청 구조가 맞물리는 부분이라, 단순히 값을 빼는 식으로 처리하지 않고 “어느 시점에 무엇을 지불하는가”를 다시 확인했습니다.

## 실패 이유와 verdict 등급 명확화

마지막으로 verdict 결과가 조금 더 설명 가능해졌습니다. 기존에는 실행이 실패했다는 사실은 알 수 있어도, 왜 실패했는지 바로 파악하기 어려운 경우가 있었습니다. 또한 반환된 verdict가 어떤 등급인지 명확하지 않으면, 호출하는 쪽에서 결과의 심각도를 판단하기도 어렵습니다.

이제 실패 결과에는 원인을 함께 전달하고, 해당 verdict의 grade도 드러내도록 개선했습니다. 사용자는 단순한 실패 여부를 넘어 다음 행동을 결정할 수 있고, 개발자는 로그를 다시 깊게 추적하기 전에 문제의 범위를 좁힐 수 있습니다.

이번 세 작업은 모두 경계 상태를 더 솔직하게 표현하는 개선이었습니다. 승인 여부, 읽기 실패, 반복 비용, 실패 원인처럼 평소에는 잘 보이지 않던 정보가 실제 운영에서는 가장 중요한 단서가 되곤 합니다. 앞으로도 성공 경로만 매끄럽게 만드는 데 그치지 않고, 실패하거나 애매한 순간에도 `vica`가 현재 상태를 제대로 설명하도록 다듬어가겠습니다.
