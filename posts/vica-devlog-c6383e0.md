# 비용은 더 정확하게, 검증은 더 까다롭게

이번 작업에서는 `vica`가 단순히 결과를 만들어 내는 데서 그치지 않고, **어떤 모델을 사용할지 판단하고, 결과를 얼마나 신뢰할 수 있는지 확인하며, 실행 상태를 안전하게 기억하는 구조**를 다듬었습니다. 겉으로 보이는 기능보다 내부 운영 방식에 가까운 변경이 많았지만, 장기적으로는 비용과 신뢰성 모두에 영향을 주는 중요한 작업이었습니다.

## 모델 라우팅과 비용 계산 개선

제품에서 사용하는 모델을 작업 성격에 맞게 라우팅할 수 있도록 흐름을 정리했습니다. 모든 요청에 같은 모델을 사용하는 방식은 구현은 간단하지만, 난도가 낮은 작업에도 비싼 모델을 호출하거나 복잡한 작업에 충분하지 않은 모델을 배정할 수 있습니다. 이번에는 제품이 사용하는 모델을 구분하고, 실행 중 모델이 전환될 때 발생하는 비용까지 계산 대상에 포함했습니다.

특히 비용을 단순 호출 횟수가 아니라 **실제로 검증된 작업을 기준으로 지불하는 방향**에 맞췄습니다. 결과가 생성됐다는 사실만으로 비용을 인정하면 실패하거나 품질이 확인되지 않은 실행까지 과금될 수 있기 때문입니다. 이제 비용은 모델 선택, 전환, 검증 결과와 더 밀접하게 연결됩니다.

물론 이 구조가 완성됐다고 보기는 어렵습니다. 라우팅 기준이 실제 사용 패턴과 잘 맞는지, 모델 전환 비용이 기대한 만큼 절감 효과를 내는지는 운영 데이터를 더 봐야 합니다. 다만 비용을 사후 집계하는 수준에서 벗어나, 제품의 의사결정 과정 안으로 끌어왔다는 점은 의미가 큽니다.

## “통과”를 다시 의심하는 검증

검증 영역에서는 테스트나 실행이 통과했을 때 한 번 더 질문하도록 만들었습니다. 핵심은 **이 검증 기준이 실제 결함을 발견할 수 있었는가**입니다.

성공 결과만 보면 모든 것이 정상처럼 느껴지지만, 기준이 지나치게 느슨하다면 결함이 있어도 그대로 통과할 수 있습니다. 그래서 통과 여부 자체와 별개로, 사용한 기준이 결함에 민감했는지를 되묻는 단계를 추가했습니다. 쉽게 말해 “정답이 나왔는가?”뿐 아니라 “틀렸다면 알아챌 수 있었는가?”도 확인하는 셈입니다.

이 변화는 검증을 조금 더 까다롭게 만들 수 있습니다. 실행 시간이 늘거나 기존에는 통과하던 작업이 재검토 대상으로 분류될 가능성도 있습니다. 그래도 검증된 작업만 비용으로 인정하려면, 검증 자체의 품질을 확인하는 과정은 꼭 필요했습니다.

## 다중 데몬 환경의 메모리 보호

안정성 측면에서는 두 데몬이 동시에 동작할 때 서로의 메모리를 지우는 문제를 수정했습니다. 각각은 정상적인 정리 작업을 수행한다고 생각하지만, 저장 영역이나 수명 주기를 제대로 구분하지 않으면 다른 프로세스가 유지해야 할 상태까지 삭제할 수 있습니다.

이런 문제는 단일 실행에서는 잘 드러나지 않고, 여러 데몬이 겹쳐 동작할 때 간헐적으로 나타나서 특히 까다롭습니다. 이번 수정으로 메모리 정리 책임이 충돌하지 않도록 해, 병렬 실행에서도 상태가 예기치 않게 사라지지 않게 했습니다.

이번 세 작업은 결국 하나의 방향을 가리킵니다. **상태는 안전하게 보존하고, 결과는 제대로 검증하며, 확인된 가치에만 비용을 쓰는 것**입니다. 화려한 기능 추가는 아니지만, `vica`를 실제로 오래 운영하기 위해 필요한 기반을 한층 단단하게 만든 업데이트였습니다.
