# Vica 개발일지: 채팅의 직접 호출과 CLI 로그인 연결

2026년 11월 3일, `vica`의 최근 커밋 세 개에서는 채팅의 실행 방식과 로그인 선택 기준을 손봤습니다. Vica가 직접 모델을 호출하는 코드 에이전트로 채팅을 확장하고, CLI 로그인이 있으면 기본으로 사용하도록 바꿨습니다. Meta와 Gemini는 각자의 CLI가 응답하도록 경로를 나눴고요. 이번 글은 커밋 메시지에서 확인할 수 있는 변경을 기능별로 묶어 정리했습니다.

## 채팅: Vica가 직접 모델을 호출하는 코드 에이전트

채팅 영역의 중심 변화는 Vica가 직접 모델을 부르는 코드 에이전트로 올라갔다는 점입니다. 채팅 안에서 Vica가 모델 호출을 맡는다는 것이 이번 변경의 핵심입니다.

다만 ‘코드 에이전트’라는 이름만으로 파일 수정이나 명령 실행까지 지원한다고 설명하기는 어렵습니다. 제공된 커밋 메시지에는 구체적인 도구 목록이나 실행 권한, 작업 완료 조건이 나오지 않습니다. 그래서 이번 기록에서는 직접 모델을 호출하는 구조로 채팅을 확장했다는 범위까지만 다루겠습니다.

이 구분은 이후 개발 기록에서도 중요합니다. 모델에 요청을 보내는 기능과, 모델의 응답을 받아 실제 코드 작업을 수행하는 기능은 각각 확인할 내용이 다르기 때문입니다. 이번 커밋은 그중 채팅의 직접 호출 역할을 명시했습니다.

## 로그인과 응답 경로: 기존 CLI 연결을 기본으로

로그인 선택에는 CLI 로그인 상태를 기본으로 활용하는 규칙이 들어갔습니다. CLI 로그인이 있는 경우 이를 기본으로 쓴다는 조건부 동작입니다. 이미 연결된 로그인 정보를 채팅의 기본 선택에 반영하려는 방향으로 읽을 수 있습니다.

여기서 ‘기본’의 범위를 넓혀 해석하지는 않으려고 합니다. CLI 로그인이 없을 때 어떤 경로를 쓰는지, 여러 로그인이 함께 있을 때 무엇을 우선하는지는 커밋 메시지만으로 알 수 없습니다. 인증이 만료됐거나 호출에 실패했을 때의 처리 역시 이번 자료에는 드러나지 않습니다.

응답을 맡는 경로에는 제공자별 구분도 생겼습니다. Meta와 Gemini는 각각 자기 CLI가 답하도록 했습니다. 따라서 이번 변경을 “모든 모델을 Vica가 동일한 방식으로 직접 호출한다”라고 요약하면 정확하지 않습니다. Vica의 직접 호출 기능과 함께, Meta·Gemini의 자체 CLI 응답 경로를 구분해서 봐야 합니다.

로그인 선택과 응답 주체도 나눠 볼 필요가 있습니다. 전자는 어떤 로그인 상태를 기본으로 사용할지에 관한 규칙이고, 후자는 어느 경로가 답을 생성하는지에 관한 규칙입니다. 두 변경을 함께 기록해야 채팅 동작을 설명할 때 이 둘을 혼동하지 않을 수 있습니다.

## 개발 기록: 직접 에이전트와 Claude 로그인

`vibe` 영역에는 채팅 직접 에이전트와 Claude 로그인에 관한 기록을 남겼습니다. 실행 기능의 변경과 별도로, 관련 내용을 개발 기록에도 반영한 작업입니다.

다만 이 커밋을 Claude 로그인 기능을 새로 구현했다는 뜻으로 보기는 어렵습니다. 메시지에서 확인되는 것은 ‘기록을 남겼다’는 사실입니다. 기록의 구체적인 내용이나 Claude 로그인과 채팅 호출을 연결하는 방식까지는 이번 자료로 설명할 수 없습니다.

이번 세 커밋은 채팅의 역할, CLI 로그인 기본 선택, 제공자별 응답 경로를 함께 다뤘습니다. 구현 결과를 평가하려면 실제 호출 흐름과 실패 처리도 확인해야겠지만, 적어도 변경 방향은 분명합니다. Vica가 직접 모델을 호출하는 역할을 맡으면서도 Meta와 Gemini의 자체 CLI 경로는 따로 두는 구성입니다. 이번 개발일지에서는 그 경계와 기록에 남은 범위를 기준으로 정리했습니다.
