# 30일 회고: AI를 도구가 아니라 동료로 쓰는 법

30일 뒤 남은 결론은 하나였습니다. AI를 동료처럼 쓰되, 동료로 믿으면 안 됩니다.

처음에는 프롬프트를 길게 쓰면 결과가 좋아진다고 생각했습니다. 틀렸습니다. 문제는 지시문의 길이가 아니라 작업을 넘기는 방식이었습니다.

사람 동료에게는 목표, 배경, 마감, 금지 사항을 설명합니다. AI에는 한 줄을 던지고 완성된 결과를 기대했습니다. 실패할 만했습니다.

---

## 1일부터 7일까지, 프롬프트 대신 작업 계약을 만들었습니다

![긴 프롬프트 대신 완료 조건까지 담은 작업 계약](/images/30-day-ai-collaboration-retrospective/01.png)
*요청보다 계약*


첫 주에는 질문을 잘 쓰는 일부터 멈췄습니다. 대신 작업을 시작하기 전에 여섯 가지 조건을 먼저 기록했습니다.

```yaml
goal: 이 작업이 해결해야 할 문제
input: 사용 가능한 자료와 출처
constraints: 금지된 주장과 변경 범위
output: 파일 형식과 필수 항목
done_when: 완료를 판단할 검사 조건
owner: 최종 승인자
```

`done_when`이 빠지면 AI는 그럴듯한 지점에서 작업을 끝냈습니다. 문장은 매끄러웠지만 출처, 예외 조건, 승인 책임이 남았습니다.

이번 글의 지식베이스가 좋은 사례였습니다. 보안 사고와 시장 전망에 관한 주장 다섯 개가 있었지만, 직접 연결된 원문은 0개였습니다.

정확한 기사, 날짜, 인물도 검색 결과에서 확인되지 않았습니다. 그래서 해당 내용을 사실로 인용하지 않았습니다. 사건 발생 여부부터 재검증 대상으로 분리했습니다.

도구처럼 썼다면 다섯 주장을 요약했을 것입니다. 동료처럼 쓰려면 먼저 자료의 빈칸을 찾아야 합니다.

## 8일부터 20일까지, 한 번의 답변을 네 역할로 나눴습니다

![조사·작성·반박·승인을 분리하고 최종 승인은 사람이 담당](/images/30-day-ai-collaboration-retrospective/02.png)
*네 단계로 분리*


두 번째 주부터 AI에게 조사와 작성, 검토를 동시에 맡기지 않았습니다. 한 세션 안에서도 역할을 분리했습니다.

| 단계 | AI가 맡은 일 | 사람이 맡은 일 | 종료 조건 |
|---|---|---|---|
| 조사 | 주장과 출처 후보 분리 | 원문 링크 직접 확인 | 출처 없는 문장 표시 |
| 작성 | 확인된 자료로 초안 작성 | 목적과 독자 적합성 판단 | 필수 항목 충족 |
| 반박 | 누락, 모순, 반례 탐색 | 반박 수용 여부 결정 | 미해결 쟁점 기록 |
| 승인 | 수정안과 차이 제시 | 배포, 병합, 전송 승인 | 사람 이름으로 승인 |

핵심은 반박 단계였습니다. “초안을 개선해 달라”보다 “이 초안이 틀릴 수 있는 지점 다섯 개를 찾아라”가 더 유용했습니다.

대화가 길어질수록 앞선 조건이 흐려지는 문제도 생겼습니다. 매 작업이 끝날 때 다음 형식으로 인수인계 문서를 남겼습니다.

```text
[목표]
[완료한 작업]
[사용한 근거]
[바꾼 파일]
[남은 불확실성]
[사람의 결정이 필요한 항목]
```

새 세션의 복구 목표는 3분으로 정했습니다. 채팅 기록을 다시 읽지 않아도 작업 상태를 설명할 수 있어야 했습니다.

AI 협업의 기억은 대화창에 있지 않았습니다. 파일, 결정 기록, 테스트 결과에 남겨야 다시 사용할 수 있었습니다.

## 21일부터 27일까지, 자율성보다 권한 경계를 먼저 정했습니다

![자율성은 모델 성능이 아니라 실패 비용으로 결정](/images/30-day-ai-collaboration-retrospective/03.png)
*실패비용 먼저*


‘동료’라는 표현에는 함정이 있습니다. 실제 동료는 실수의 책임을 나눌 수 있지만 모델은 책임질 수 없습니다.

그래서 자율성은 모델 성능이 아니라 실패 비용으로 결정했습니다. 잘하는 작업도 피해가 크면 자동 실행에서 제외했습니다.

| 위험도 | 작업 예시 | 허용 범위 |
|---|---|---|
| 낮음 | 요약, 형식 변환, 테스트 초안 | 자동 실행 후 표본 확인 |
| 중간 | 코드 수정, 쿼리 작성, 문서 변경 | 변경안 생성 후 사람 검토 |
| 높음 | 운영 배포, 외부 게시, 결제, 권한 변경 | 사람의 명시적 승인 전 실행 금지 |

읽기 권한과 쓰기 권한도 분리했습니다. 비밀키, 사용자 원문, 운영 데이터는 필요하다는 이유만으로 전달하지 않았습니다.

외부 전송, 파일 삭제, 계정 권한 변경에는 별도 승인 단계를 넣었습니다. “되돌릴 수 있는가”를 매번 먼저 확인했습니다.

제공된 보안 주장도 출처가 없었기 때문에 사고 사례로 사용하지 않았습니다. 위험을 강조하려고 검증되지 않은 사건을 사실처럼 쓰면 검증 원칙부터 무너집니다.

## 28일부터 30일까지, 만족도 대신 재현성을 평가했습니다

마지막 사흘에는 “답변이 좋았는가”라는 질문을 버렸습니다. 기분에 따라 달라지고 다음 작업에 재사용하기 어려웠습니다.

대신 네 항목을 100점 기준으로 기록했습니다.

| 평가 항목 | 비중 | 측정 방법 |
|---|---:|---|
| 근거 충실도 | 35점 | 원문과 다른 주장 수 확인 |
| 재현 가능성 | 25점 | 새 세션에서 같은 절차 실행 |
| 수정 대응 | 20점 | 지적 후 반복된 오류 수 기록 |
| 실제 시간 절감 | 20점 | 시작부터 사람 승인까지 분 단위 측정 |

측정하지 않은 개선률은 쓰지 않았습니다. 이번 기록에는 30일 전후의 완료 시간과 오류율이 없기 때문입니다.

대신 운영 방식은 분명하게 바뀌었습니다. 요청 한 줄은 작업 계약으로 바뀌었고, 단일 답변은 조사·작성·반박·승인의 네 단계로 분리됐습니다.

동료처럼 쓴다는 말은 친근하게 대화한다는 뜻이 아니었습니다. 맥락을 공유하고, 반박을 요청하고, 결과를 기록한다는 뜻이었습니다.

최종 책임은 그대로 남았습니다. AI 초안과 검토 기록은 저장하지만, 배포와 병합의 승인 칸에는 사람 이름만 적습니다.
