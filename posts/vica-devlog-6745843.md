# vica 개발일지: 애매한 경계를 계약과 검증으로 바꾸기

8월 7일부터 8일까지는 새로운 기능을 크게 늘리기보다, `vica`가 실제 환경에서 지켜야 할 동작을 더 명확하게 만드는 데 집중했습니다. 코드가 “대체로 잘 돌아가는지” 확인하는 수준을 넘어, 병합 규칙과 처리량 제어, 터미널 실행 경로, 실제 코퍼스 성능을 지속적으로 검증하도록 다듬었습니다.

## 컨텍스트 병합 규칙 명문화

컨텍스트를 합치는 과정에서 `INV-CX4`에 해당하는 상황을 만나면 병합을 거부하던 동작을 수정했습니다. 이전 구현은 위험해 보이는 입력을 차단한다는 점에서는 보수적이었지만, 정작 어떤 방식으로 합쳐야 하는지 정의하지 않은 채 처리를 포기하는 셈이었습니다.

이번에는 해당 불변 조건이 요구하는 병합 규칙을 코드에 직접 반영했습니다. 핵심은 예외적인 조합을 무조건 실패로 돌리는 것이 아니라, 충돌 상황에서도 일관된 결과를 만들 수 있도록 우선순위와 보존 범위를 명시하는 것이었습니다. 덕분에 호출하는 쪽에서 불필요한 우회 처리를 만들 필요가 줄었고, 컨텍스트 계층의 책임도 조금 더 선명해졌습니다.

솔직히 이런 수정은 코드 몇 줄보다 “무엇이 올바른 결과인가”를 합의하는 과정이 더 어렵습니다. 다만 규칙이 코드로 남았기 때문에 앞으로 비슷한 사례가 추가되더라도 같은 기준으로 판단할 수 있게 됐습니다.

## 데몬의 백프레셔 계약 검증

데몬 테스트는 시간 측정 중심에서 동작 계약 중심으로 바꿨습니다. 기존 방식은 두 구간의 소요 시간을 재서 백프레셔가 작동한다고 간접적으로 판단했습니다. 하지만 실행 환경이나 스케줄러 상태에 따라 결과가 흔들릴 수 있고, 테스트가 통과해도 실제로 어떤 보장이 검증된 것인지 분명하지 않았습니다.

이제는 생산 속도가 소비 능력을 넘어설 때 데몬이 작업을 무한히 밀어 넣지 않는지, 처리 여유가 생기기 전까지 올바르게 제어되는지를 직접 확인합니다. “몇 밀리초 이상 걸렸는가”가 아니라 “부하가 걸렸을 때 약속한 상태 전이가 발생했는가”를 보는 셈입니다. 테스트 안정성뿐 아니라, 향후 내부 구현을 바꾸더라도 반드시 유지해야 할 계약이 무엇인지 드러났다는 점이 가장 큰 수확입니다.

## 실제 터미널 경로를 통과하는 E2E 테스트

E2E 테스트도 현실에 한 걸음 더 가까워졌습니다. 라이브러리나 내부 진입점을 직접 호출하는 우회 경로 대신, 실제 바이너리를 실행하고 터미널을 통해 입력과 출력을 주고받도록 변경했습니다.

CLI 프로그램은 TTY 여부, 버퍼링, 종료 신호, 표준 입출력 연결 방식에 따라 예상과 다르게 움직일 수 있습니다. 내부 API만 검증하면 이런 문제를 놓치기 쉽습니다. 이제 사용자가 실행하는 것과 유사한 경로를 통과하므로, 바이너리 패키징부터 대화형 동작까지 한 흐름으로 확인할 수 있습니다. 테스트 구성은 조금 더 무거워졌지만, E2E라는 이름에 훨씬 정직한 검증이 됐습니다.

## 실제 코퍼스 KPI를 상시 품질 게이트로

마지막으로 실제 코퍼스 기준의 탐지율을 복구하고, 이를 일회성 확인이 아닌 상시 게이트로 고정했습니다. 합성 데이터만으로는 잘 드러나지 않는 표현과 경계 사례를 실제 데이터가 계속 붙잡아 주도록 한 것입니다.

앞으로 관련 로직을 수정할 때 테스트 몇 개가 통과하더라도 실제 탐지 성능이 기준 아래로 떨어지면 바로 알 수 있습니다. 숫자를 좋아 보이게 만드는 것보다, 회귀를 숨기지 않는 안전장치를 세우는 데 의미를 뒀습니다.

이번 작업들은 화려하지 않지만 모두 같은 방향을 향합니다. 모호한 처리는 규칙으로, 타이밍 추측은 계약으로, 우회 테스트는 실제 실행으로, 일시적인 성능 확인은 지속적인 품질 기준으로 바꿨습니다. 이런 기반이 쌓일수록 다음 기능을 더 안심하고 추가할 수 있을 것 같습니다.
